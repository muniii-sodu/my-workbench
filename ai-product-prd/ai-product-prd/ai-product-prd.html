CORE DIFFERENCE

传统PRD vs AI PRD：六大本质差异

传统PRD是在描述一个确定的系统；AI产品PRD是在设计一套"面对不确定性，仍能稳定交付业务价值的机制"[2]。传统软件是"基于规则"（Rule-based），AI产品是"基于推理"（Inference-based），本质上是概率性的[3]。

维度 传统PRD AI产品PRD
核心逻辑 消除不确定性，输入A必出B 管理不确定性，概率性输出
交互结构 用户-产品 二元交互 用户-模型-产品 三元结构[4]
叙事核心 用户故事（User Story） Agent故事（Agent Story）+ 模型旅程[4]
流程设计 线性流程图（点击→API→返回） 网状工作流（DAG/状态机/ReAct循环）[3]
验收标准 功能做完了（按钮/流程/数据） 效果达标了（准确率/幻觉率/采纳率）[2]
交付物 功能点（Feature） 能力（Capability）+ 4个交付物[3]
"传统PRD关注'人如何使用产品'，AI PRD更关注'产品如何让模型可靠完成任务'。"[4]
DEEP DIVE

九大模块深度拆解

01
价值阐述：为什么一定要用AI？
不是所有问题都需要大模型

库存低于安全线自动预警，规则引擎更稳定；销量预测，机器学习可能更合适；补货量和运输路径计算，往往需要运筹优化。大模型真正擅长的是理解语言、检索知识、解释推理和跨系统完成任务[2]。

AI产品PRD不能只写"接入某个模型"，还要写清楚：现有方案有什么瓶颈？不引入AI会怎样？AI究竟比规则、算法或人工多创造了什么价值？

核心原则 问题决定技术方案，而不是模型热度决定产品方案。先回答"为什么用AI"，再回答"怎么用AI"。
02
需求描述 → Agent Story：定义模型的"思考剧本"
从"用户要什么"改成"Agent怎么干"

传统用户故事太单薄，只说"要什么"，没说"怎么做"。Agent Story要讲清模型的"思考剧本"，核心是ITTO模型（Input, Thought, Tool, Output）[3]。

ITTO要素 定义 关键内容
Input 输入 定义上下文边界 显性输入（用户Query）+ 隐性上下文（用户画像/环境状态/会话历史/检索范围）
Thought 思考 定义推理拓扑结构 意图识别 + 槽位提取 + 推理约束（什么不能做）
Tool 工具 定义行动触手 工具选择 + 参数映射 + 异常处理（超时/无数据怎么回复）
Output 输出 定义呈现形态 内容格式（文本/JSON/卡片）+ 语气人设 + UI组件触发
实战案例："查物流"需求改写 传统用户故事："用户点'查看物流'，跳转详情页。"
Agent Story（ITTO版）：Input: 用户Query"我的鞋到了吗？" + 上下文(User_ID:12345, 最近订单:Order_A含跑鞋) → Thought: 识别意图Check_Logistics, 匹配"鞋"到Order_A, 推理用户极大概率问Order_A → Tool: 调用Logistics_API(order_id='Order_A') → Output: "亲，您购买的耐克跑鞋（订单尾号8899）正在派送中" + 渲染Logistics_Card显示地图轨迹[3]。
03
业务流程和系统流程：线性→网状
流程图里要多出"AI"和"人工"两个角色

B端AI很少能够100%自动化。用户真正关心的是：AI在哪一步介入？做完以后谁确认？出错以后谁接手？[2]

传统线性流程无法涵盖AI的灵活性，需要设计基于状态机或DAG（有向无环图）的工作流。目前业界最主流的Agent工作流模式是ReAct (Reason + Act)，核心是"思考-行动-观察"循环[3]。

传统线性流程

用户点击 → 调API → 读写数据库 → 返回结果。一条路走到底，没有分支。

AI网状工作流

用户表达意图 → Agent感知理解 → 推理规划 → 动态调用工具 → 生成回答。每步都可能分支、循环、回退。

人在回路（HITL）三节点 审核节点：高风险操作（退款/群发邮件）AI生成草稿后暂停等待人工确认；澄清节点：置信度低于阈值时进入反问模式列出选项；接管节点：检测到用户愤怒或连续三次未解决问题时强制转人工[3]。
04
模型选型：六维度评估
平衡性能、成本和可扩展性

做技术选型时，要平衡性能、成本和可扩展性[3]。关键维度包括：

维度 评估问题
性能模型在目标任务上的准确率/延迟/吞吐量是否达标？
适配性模型是否支持所需的语言、格式、工具调用能力？
可扩展性能否支持未来新增工具、新增场景、多Agent协作？
稳定性API可用性SLA？模型版本迭代是否会破坏现有功能？
成本Token计费方式？单次交互成本？月度预估费用？
合规数据是否出境？是否满足行业监管要求？是否有内容审核？
LLM级联策略 先用弱模型（低成本），搞不定再用强模型（高成本）。这么做，强模型调用成本能省一半以上[3]。
05
Prompt工程：AI的"软代码"
五段式标准模板

提示词不是"玄学"，有固定模板。System Prompt按以下结构编写，少一个都容易出问题[3]：

// System Prompt 五段式标准模板 1. 角色定义 "你是专业的电商客服助手，擅长处理订单查询和售后问题。" 2. 核心任务 识别用户意图 → 提取订单号 → 调用工具查询 → 解析数据返回 3. 核心挑战 - 信息缺失：用户未提供订单号时如何追问 - 工具失败：API超时/无数据时如何兜底 - 多义意图："查快递"是查最新还是历史订单 4. 约束 - 不准编造数据，不知道就说不知道 - 不准输出未经API验证的物流节点 - 输出控制：JSON（给系统）+ 自然语言（给用户） 5. Few-shot 示例 Input: "我的鞋到了吗？" → Output: {"intent":"check_logistics","entity":"鞋","action":"query_recent_order"}
三个高级技巧 1. 强化专业身份+Checklist强制按步骤思考（思维链）；2. Prompt压缩+级联策略（2428 tokens压到331 tokens，压缩比7.3倍）；3. LLM级联先用弱模型再用强模型（成本省50%+）[3]。
06
训练数据集：数据是源泉，不是附件
别用平庸数据，要定义"理想态"

企业知识库没有更新，AI就会引用过期制度；历史工单分类混乱，模型就会学到错误规律；客户数据没有做好隔离，再高的准确率也没有意义[2]。

很多人直接用历史客服数据训练，这是大错——那些数据里藏着大量低质量回复，只会越训越差。正确做法：筛选高质量样本，标注"理想回答"[3]。

"理想态"定义法 人工响应<5秒，AI目标就得设成<2秒；人工解决率80%，AI要冲95%。用"理想回答"而非"历史回答"作为训练标准，让模型向最佳实践看齐而非向平均水平妥协[3]。
07
评测体系：三层评测 + 效果门槛
技术达标不等于产品落地

评测分三层，成本和效果兼顾[3]：

L1
代码自动评
查格式、JSON合法性、字段完整性。快又省成本，可CI/CD集成。
L2
人工评
MVP阶段找专家看逻辑、推理链、边界处理。LLM-as-Judge辅助。
L3
业务评
看转人工率、解决率、采纳率、节省时间。真实业务指标。
评估维度 技术层面 产品层面
核心指标 准确率、幻觉率、响应时间、安全性、调用成本 建议查看率、采纳率、用户修正率、节省时间/成本[2]
关键洞察 如果推荐准确率达到90%，用户采纳率却只有20%，问题可能不在模型，而在推荐理由不透明、入口不符合工作习惯，或用户不愿承担责任[2]。技术达标不等于产品落地。
08
效果保障与稳定性策略：三层能力边界 + 数据飞轮
不只写"能做什么"，还要写"不能做什么"

PRD必须定义三层边界，边界写得越清楚，研发越好实现，业务越敢使用[2]：

边界层级 定义 典型场景
自动执行 风险低、结果可逆 查物流、文档分类、信息检索
推荐+确认 涉及金额/客户权益/重要决策 AI给建议，人来拍板
禁止触碰 不可逆操作/敏感信息 资金账户、敏感信息、删除操作
数据飞轮迭代闭环 用户使用 → 反馈沉淀（采纳/修改/驳回/转人工）→ Bad Case标注 → 数据和方案优化 → 效果提升[2]。PRD需要提前规定：记录哪些行为？谁来标注Bad Case？知识库多久更新？Prompt、规则和模型分别在什么情况下调整？
09
产品功能原型图：Chat+GUI，预留"思考中"状态
别只做聊天框

交互上别只做聊天框，要Chat+GUI。比如报修时，弹出卡片让用户选时间，省一半沟通时间[3]。

如果思考过程很长（涉及多步推理和多次搜索），产品界面上必须有对应的"思考中"反馈（如流式输出思考过程），否则用户会以为系统卡死[3]。

LLM产品别搞瀑布流，要Demo驱动 快速做Demo拿反馈，比写100页PRD管用。提示词即代码，改一行Prompt就能迭代[3]。
FULL TEMPLATE

Agent型AI产品PRD完整模板

Agent型产品必须以模型故事和工作流程为核心。以下是针对Agent型AI产品的推荐PRD模板，控制在5-6个主要章节，强调模型中心设计[4]。

Chapter 1
需求背景与产品定位

描述业务痛点、市场机会、技术可行性。核心价值量化（如"降低自动化开发门槛，提升效率30%以上"）。技术可行性说明（基于开源LLM+LangChain/ReAct框架）。

Chapter 2
用户场景与模型故事

淡化细粒度用户旅程，聚焦典型场景下的模型行为。每个模型故事末尾增加"上下文构建策略"：短期记忆（对话轮次）、长期记忆（RAG检索）、工具结果注入[4]。

Chapter 3
Agent工作流程设计（核心新增模块）

流程图（外部视角）：用户输入→意图解析→任务分解→并行工具调用→结果聚合→验证与迭代→输出报告。时序图（内部视角）：标注每个节点的数据传递格式（JSON Schema）和超时/错误处理。多Agent协作机制：黑板式共享内存或消息队列[4]。

Chapter 4
功能清单与实现细节（含提示词设计）

列出核心功能，并为每个关键Agent节点提供提示词模板。采用"角色-挑战-策略-完整提示词-输出控制"五段式。输出控制：严格遵循工具Schema，失败时返回{error: "...", retry_strategy: "..."}[4]。

Chapter 5
评估标准、测试数据集与风险管控

评估维度：任务完成率（端到端）、单步准确率、幻觉率、格式符合率、执行耗时、成本。测试数据集：正常案例100条+边界案例（模糊指令/长上下文/冲突需求）+对抗案例（诱导幻觉）。风险与缓解：幻觉→验证Agent+事实核查、上下文丢失→RAG+总结压缩、工具失败→备用方案+用户介入[4]。

Chapter 6
非功能需求与上线计划

性能（延迟<10s）、成本控制（单次交互<$0.05）、安全合规（数据隐私）、可扩展性（支持新工具插件）。预留"迭代发现"章节，记录上线后新风险及解决方案[4]。

PRODUCT TYPES

嵌入型 vs Agent型：不同产品不同写法

嵌入型AI产品（如老产品新增AI客服）可以保留传统PRD结构，但必须额外增加三个关键板块。Agent型产品则必须进行结构性重构[4]。

维度 嵌入型AI产品 Agent型AI产品
AI角色 固定环节嵌入现有流程（类似调API） 主动分解任务、调用工具、迭代优化
输入输出 相对固定 动态变化，多模态
PRD结构 传统结构 + 3个补充板块 结构性重构，以模型故事为核心
新增板块 1.AI引入可行性分析 2.提示词设计逻辑 3.评估和测试标准 1.Agent Story(ITTO) 2.Agent工作流 3.提示词设计 4.评估指标+数据集
典型产品 AI摘要、AI客服、AI写作辅助 deer-flow、Manus、AutoGPT类
PITFALLS

常见坑点与避坑指南

坑1过度依赖模型自主性而缺少兜底逻辑
模型不是万能的，必须有异常兜底。每个Agent节点都要定义：工具调用失败怎么办？置信度低于阈值怎么办？用户连续否定怎么办？[4]
坑2测试集过于理想
只用正常案例测试，上线后被真实用户的模糊指令、对抗输入打爆。必须包含边界案例（模糊指令/长上下文/冲突需求）和对抗案例（诱导幻觉）[4]
坑3忽略生产环境下的成本与延迟
Demo阶段用GPT-4跑得好好的，上线后发现每次交互成本$0.5，延迟8秒。PRD必须提前定义成本上限和延迟门槛，设计LLM级联策略[4]
坑4上下文构建策略不完善
很多项目上线后模型胡说八道，原因是PM在定义输入时忽略了提供"当前库存数据"等隐性上下文，导致模型只能根据训练数据中的过时信息猜测[3]
坑5把传统PRD里的"系统"换成"AI"就完事
原来写"系统根据规则生成结果"，改成"AI生成结果"——这是最常见的错误。AI产品PRD需要把能力边界、数据、人机协作、效果评估、风险兜底和持续运营全部纳入产品设计[2]

核心认知转变

传统软件PM的核心是"消除不确定性"；AI PM的核心是"管理不确定性"。AI PM不再是扣像素，而是定义模型的思考方式——从"功能定义者"变成"认知架构师"[3]。

一份高质量的AI PRD，不是功能列表堆砌，而是系统回答：我们如何把模型不确定性转化为可靠生产力[4]。

CHECKLIST

AI产品PRD自检清单

价值与边界

  • 为什么用AI：现有方案瓶颈明确，AI比规则/算法/人工多创造的价值量化
  • 能力边界三层：自动执行 / 推荐+确认 / 禁止触碰，每项有典型场景
  • 不做什么：明确AI不能做的事，比能做什么更重要

模型与数据

  • Agent Story：用ITTO模型定义每个关键场景的输入/思考/工具/输出
  • 模型选型六维度：性能/适配性/可扩展性/稳定性/成本/合规均有评估
  • Prompt五段式：角色-挑战-策略-完整提示词-输出控制，含Few-shot示例
  • 数据理想态：用"理想回答"而非"历史回答"作为标准，定义数据来源/格式/更新频率/质量标准

流程与评测

  • 网状工作流：用DAG/状态机替代线性流程图，标注HITL三节点
  • 三层评测：代码自动评 + 人工评 + 业务评，每层有明确指标和门槛
  • 测试数据集：正常案例+边界案例+对抗案例，200-500条典型规模
  • 效果门槛：技术层面（准确率/幻觉率/延迟/成本）+ 产品层面（采纳率/修正率/节省时间）

稳定性与迭代

  • 异常兜底：工具失败/置信度低/用户否定的每种异常路径都有处理方案
  • 数据飞轮：用户行为记录→Bad Case标注→数据/方案优化→效果提升的闭环已定义
  • Chat+GUI：不只是聊天框，有卡片/图表等GUI组件，预留"思考中"状态
